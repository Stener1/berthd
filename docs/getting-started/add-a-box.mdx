A **box** is any machine your agents run on, usually Linux: a VPS, a cloud
VM, the desktop under your desk. It runs `berthd`, Berth's daemon, as a user
service.
The laptop pairs with it once and from then on talks to it over pinned mutual
TLS; it never needs SSH to reach the box, and at most uses it once, to install.

## What a box needs

- Linux (or macOS) on amd64 or arm64
- `git` (repositories and worktrees) and `tmux` (sessions). A fresh Ubuntu
  has neither: [over SSH](#over-ssh) Berth puts its own tmux on the box (no
  sudo) and installs git in a terminal where `sudo` asks for your password;
  the install command offers to install both with `sudo` when it can ask,
  and otherwise stops with the command to run
- a [Tailscale](https://tailscale.com) address, unless you choose to listen
  elsewhere (see [Where berthd listens](#where-berthd-listens))
- the agent CLIs you want to run (`claude`, `codex`, …): setting a box up
  over SSH installs the ones you pick; and optionally `cloudflared` for
  public shares

## This Mac

No server yet? The Mac the app runs on can be your first box. In the app,
**Start on this Mac** (the first-run setup's first choice) and **Use this
Mac** (in **Add a box**) set it up with one click and no terminal:

1. It copies the `berthd` the app carries (a universal build, signed and
   notarized with the app) to
   `~/Library/Application Support/berth/bin/berthd`. launchd runs the program
   its service names, and a path inside `Berth.app` changes when the app
   updates or moves, so the service never points into the app. The copy is
   checked against its signature (`codesign --verify`) before it runs.
2. It runs `berthd install` from there, listening on `127.0.0.1` only, on
   the first free port from 7445 (7444, the usual port, is left alone). berthd
   becomes your launch agent, `dev.berth.berthd`, with its state in
   `~/Library/Application Support/berth/box`, and the
   [hooks that report agent state](/getting-started/first-agent#let-the-box-report-agent-state)
   go in for the agent CLIs on this Mac.
3. It pairs this laptop with it: `berthd pair --json` hands the link straight
   to `berth pair`. Nothing to copy.

The box is named after this Mac's hostname and marked **This Mac** in
Settings → Boxes. The next step, adding a project, opens on this Mac's own
folders.

<Callout title="Agents run while the Mac is awake">
  A box on your Mac runs agents only while the Mac is awake: they pause when
  it sleeps, and carry on when it wakes. For agents that keep working with
  the lid closed, add a server later; your projects on this Mac stay.
</Callout>

Setting up again is safe: each step is skipped when it is done, so it only
reconnects. Some cases it handles on its own:

- **berthd already installed** with [the install command](#with-the-install-command)
  (`~/.local/bin/berthd`, the same launch agent): it is used, not installed a
  second time, and upgraded in place when the app carries a newer release.
- **The port was taken** since: berthd moves to the next free one.
- **App updates.** The laptop agent compares the copy with the `berthd` in
  the app when it starts and every few minutes, and after an update replaces
  the copy and reinstalls with `--keep-listen`. Agent sessions keep running.
- **No login session.** launchd needs you logged in at the Mac (screen
  sharing counts); over SSH alone, setting up says so and changes nothing.

To stop, open Settings → Boxes, the box's **…** menu, **Stop using this
Mac…**: Berth forgets the box, stops berthd and removes its launch agent, and
deletes the copy. Its data (keys, projects list, session records) stays
unless you tick **Also delete its data**. Your repositories are never touched.

## On your tailnet

When this Mac runs [Tailscale](https://tailscale.com), **Add a box** (and the
first-run setup) opens with the machines on its tailnet: the tailnet's name,
then each Linux or macOS machine with a dot for online or offline, and
**Paired as …** on the ones that already are boxes. Phones and other devices
that can't run berthd are left out; a long list gets a filter.

**Set up** on a Linux machine asks who to log in as (your user on this Mac,
or the `User` your `~/.ssh/config` gives that host; change it if the box's
user differs) and what to call the box, then runs
[`berth add ssh`](#over-ssh) to the machine's MagicDNS name with its output
as it goes. berthd listens on the machine's tailnet address only, so there is
nothing to open to the internet and nothing to choose.

- **Tailscale SSH.** Machines running Tailscale SSH (`tailscale set --ssh`)
  are marked; the tailnet's SSH rules decide who logs in, and no keys are
  needed. Their host keys come from the tailnet itself, so a first login
  trusts the key without asking when it is the one the tailnet reports. When
  your rules ask for a check, Berth opens the approval page in your browser
  and carries on once you approve.
- **A Mac on the tailnet.** `berth` carries only the Linux daemons, so for a
  Mac the screen points to [the install command](#with-the-install-command)
  instead.
- **Offline machines** are listed, greyed out, until they come back.

The same list from a terminal:

```sh
berth discover            # the machines on this Mac's tailnet, and which are boxes
berth add ssh me@dev-box  # what Set up runs
```

When Tailscale isn't installed, is signed out or is turned off on this Mac,
the screen shows the install command first and **Or use Tailscale** below it,
with a link to get Tailscale or a note to sign in from its menu bar icon.
Coming back to the app checks again.

**Sign in to another tailnet**, beside the list, adds a tailnet this Mac's
Tailscale isn't on (a personal one while the Mac is on work's, say): Berth
signs in to it with its own embedded node (see
[Boxes on another tailnet](#boxes-on-another-tailnet)), and its machines
appear in the list under a tab of their own, set up the same way.

## With the install command

On the box, as the user your agents will run as (no root needed):

```sh
curl -fsSL https://berthd.app/install | sh
```

It downloads the latest `berthd` for the box's platform from GitHub, checks
it against the release's `checksums.txt`, puts it in `~/.local/bin`, and runs
`berthd install`, the same step `berth add ssh` runs: berthd becomes a user
service (systemd on Linux, launchd on macOS), and the
[hooks that report agent state](/getting-started/first-agent#let-the-box-report-agent-state)
go in for the agent CLIs it finds. Then it prints a pairing link:

```text title="The end of its output"
==> Installing berthd v0.1.0 to /home/me/.local/bin/berthd
==> Starting the service
  Installed /home/me/.config/systemd/user/berthd.service; berthd is serving on 100.101.102.103:7444.
  Agent integrations (hooks for needs-you, working and done; berth's skills):
    Claude Code: skills in /home/me/.claude/skills; hooks added in /home/me/.claude/settings.json
    Not found: Codex, Cursor Agent. After installing one, run: /home/me/.local/bin/berthd integrations install codex|cursor

berthd v0.1.0 is running. Paste this link into Berth on your laptop
(Add a box). It works once, for ten minutes:

  berth://100.101.102.103:7444?code=…&fp=…

Or on your laptop:  berth pair 'berth://100.101.102.103:7444?code=…&fp=…'

Your laptop will dial 100.101.102.103:7444. A new link any time: berthd pair
```

Paste the link into the app (**Add a box**), or run the `berth pair` line on
your laptop; more in [with a pairing link](#with-a-pairing-link). The whole
output is in [install](/getting-started/install#put-berthd-on-a-box).

### Installer options

Pass options after `sh -s --`, for example
`curl -fsSL https://berthd.app/install | sh -s -- --listen 0.0.0.0:7444`:

| Option | Environment | |
| --- | --- | --- |
| `--version vX.Y.Z` | `BERTH_VERSION` | Install that release instead of the latest |
| `--listen ADDR` | `BERTHD_LISTEN` | Where berthd listens (default: the box's tailnet address; see [below](#where-berthd-listens)) |
| `--no-pair` | `BERTH_NO_PAIR=1` | Don't print a pairing link at the end |
| `--no-integrations` | `BERTH_NO_INTEGRATIONS=1` | Don't install agent hooks and skills for the agent CLIs on the box |
| `--yes`, `-y` | `BERTH_YES=1` | Ask nothing (see below) |
| `--system` | | Put berthd in `/usr/local/bin` (the default when run as root); only the copy uses `sudo`, and `berth upgrade` then can't replace it, so upgrade by running the installer again |
| | `BERTH_BIN_DIR` | Put berthd somewhere else |

It asks at most two things, and only on a terminal: whether to listen on
every interface when the box has no tailnet address (no, unless you say so),
and on Linux whether to turn on lingering so berthd keeps running after you
log out (`sudo loginctl enable-linger $USER`). With `--yes`, or with no
terminal to ask on, it never listens on every interface unless `--listen`
says so, and turns lingering on only if `sudo` needs no password.

Run it again any time: it upgrades berthd in place and restarts the service
(agent sessions keep running), keeping the address it listens on unless
that was a tailnet address. It stops with a plain reason, and changes
nothing, when the download doesn't match its checksum, the platform isn't
amd64 or arm64 Linux or macOS, `curl`/`wget` or `tar` is missing, or systemd
has no user session for you (log in as that user directly, over SSH, rather
than through `su` or `sudo`). The script is
[`site/install.sh`](https://github.com/sean-brydon/berthd/blob/main/site/install.sh);
read it before piping it to `sh` if you like.

## Over SSH

If you can `ssh me@my-box`, Berth sets the box up from here in one guided
flow, with nothing to install on the box by hand: berthd, tmux and git when
they're missing, the agent CLIs you choose, their hooks, and the pairing.

### In the app

**Add a box › Or let Berth set it up over SSH** (or **Install and pair** on a
machine on your tailnet) opens the guided install, full screen:

1. **The plan.** What will run, step by step, with the exact commands a click
   away and the steps that may need `sudo` marked. Above it, **Agents**:
   Claude Code is ticked; Codex, Cursor Agent and OpenCode are there to add.
   Your choice is remembered for the next box.
2. **The terminal.** Open the terminal and install starts `berth add ssh` in
   a terminal on this computer, shown full screen beside a checklist of the
   steps. Press **Enter** in it to start. When `sudo` on the box asks
   for your password, the banner says so: type it in the terminal. What you
   type goes to the box through this terminal and nowhere else; Berth never
   sees, keeps or logs it.
3. **Ready.** Each step ticks as it ends. A step that fails shows what failed
   (with any command to run as a copyable line) and **Retry from here**,
   which runs again from that step; the steps before it are kept. At the end
   the box is paired, and the button goes on to it (or back to
   [Team setup](/guides/team-setup) when that's where you came from).

A login problem stops at the first step with what to do: trust a new host
key, try another key file, or install with the command on the box instead.

### From a terminal

The same flow, in your own terminal:

```sh
berth add ssh me@my-box --agents claude,codex
```

It connects, reads what the box has, prints the plan, and waits for
**Enter**:

```text title="On a fresh Ubuntu 24.04 box"
==> Connect to me@my-box
✓ Connect to me@my-box (me@my-box, linux/arm64)

Berth will set this box up:
 1. Install berthd
      upload berthd-linux-arm64 → ~/.local/bin/berthd
      ~/.local/bin/berthd install --no-tools --no-integrations --keep-listen
 2. Keep berthd running after you log out  [sudo]
      sudo loginctl enable-linger me
 3. tmux and git  [sudo]
      upload tmux-linux-arm64 → ~/.local/bin/tmux   (Berth's own build: no sudo)
      sudo apt-get update -q
      sudo apt-get install -y -q git
 4. Claude Code and Codex
      ~/.local/bin/berthd agents install claude codex
 5. Agent integrations
      ~/.local/bin/berthd integrations install present
 6. Pair with this computer

Press Enter to start, or Ctrl-C to stop.
```

Then it uploads berthd (and Berth's tmux, below), and runs the box's steps
in one terminal on the box (`ssh -t`), so `sudo` asks for your password once,
there. It ends with `Ready: paired with my-box`. Running it again is safe:
each step checks first, and on a box that is set up it only reinstalls the
service and pairs again.

What each step does:

- **berthd** goes in `~/.local/bin` and runs as your user service (systemd on
  Linux, launchd on macOS), with `~/.local/bin` on its `PATH`.
- **Lingering** (Linux): systemd stops a user's services at logout unless
  lingering is on, so it is turned on with `sudo loginctl enable-linger`,
  only if it is off.
- **tmux and git**, only what is missing. `berth` and the app carry a static
  tmux for Linux (amd64 and arm64), so a box without tmux gets that one in
  `~/.local/bin`, with no sudo. git comes from the box's package manager
  (apt, dnf, yum, pacman, zypper, apk or Homebrew) with `sudo`.
- **Agent CLIs**, without sudo, into `~/.local/bin`, each skipped when it is
  there already (`berthd agents install`):
  - Claude Code with its native installer
    (`curl -fsSL https://claude.ai/install.sh | bash`), which checks the
    build it downloads against its checksum;
  - Codex, its release binary from
    [github.com/openai/codex](https://github.com/openai/codex/releases),
    pinned to a version and checked against its sha256;
  - Cursor Agent and OpenCode with their own installers (over HTTPS; neither
    publishes checksums for them).

  Gemini CLI isn't offered: it installs with npm and needs Node.js 20 or
  newer, which Berth doesn't install. Install Node, then
  `npm install -g @google/gemini-cli`.
  If a login shell's `PATH` lacks `~/.local/bin`, one marked line adds it to
  your profile. Signing in is yours: each agent asks the first time it starts
  (Claude Code right in the chat).
- **Integrations**: the [hooks that report agent state](/getting-started/first-agent#let-the-box-report-agent-state)
  and Berth's skills, for every agent CLI on the box.
- **Pair**: `berthd pair` on the box, and this computer pairs with the link.

A box without a tailnet address asks where berthd should listen: press
**Enter** to listen on every interface (`0.0.0.0:7444`; only laptops
you pair can connect, both keys pinned), or pass `--listen`.

Berth installs as the user your agents will run as, never as root: logging in
as `root` stops at the first step and says to log in as that user (make one
with `adduser me && usermod -aG sudo me`).

### Without a terminal

With `--yes`, or with no terminal (a script, CI), nothing waits for Enter and
nothing can type a password: steps that need `sudo` use it only when it asks
for nothing, and otherwise stop with the command to run on the box:

```text
Installing git needs root, and sudo asks for a password, which Berth can't type without a terminal.
Run this on the box, then set it up again:
  sudo apt-get update -q && sudo apt-get install -y -q git
✗ tmux and git: Installing git needs root, and sudo asks for a password, which Berth can't type without a terminal.
```

Only the Linux daemons come with `berth`. For a Mac box, run
[the install command](#with-the-install-command) on it instead. From a source
build, you can also build its daemon beside the others (`amd64` for an Intel
Mac):

```sh
CGO_ENABLED=0 GOOS=darwin GOARCH=arm64 go build -o bin/berthd-darwin-arm64 ./cmd/berthd
```

Options:

| Flag | What it does |
| --- | --- |
| `--name N` | What to call the box in Berth (default: its hostname). It becomes part of URLs like `3000.N.localhost`. |
| `--agents LIST` | The agent CLIs to install: `claude`, `codex`, `cursor`, `opencode`, comma-separated, or `none` (default `claude`). |
| `--yes` | Ask nothing: don't wait for Enter, and stop with the command to run where `sudo` would ask for a password. |
| `--from STEP` | Start from a step (`berthd`, `linger`, `tools`, `agents`, `integrations`, `pair`), keeping the ones before it. It still connects first. |
| `--network NET` | Reach the box through one of [your other tailnets](#boxes-on-another-tailnet). |
| `--listen ADDR` | Where berthd listens, for a box without a tailnet address. |
| `--address ADDR` | The address the laptop should dial, when the one berthd guesses is wrong. |
| `--identity FILE` | An SSH private key to log in with, as `ssh -i`. |
| `--trust-host-key SHA256:…` | Trust a new box's host key if its fingerprint is this one. |
| `--no-integrations` | Don't install agent hooks and skills on the box. |
| `-- OPTIONS` | Anything after `--` goes to `ssh`. |

### More agents later

**Settings › Boxes**, a box's **…** menu, **Add agents…** adds agent CLIs to
a box that is already set up, in the same view: the agents to choose (the
ones there are ticked and marked), then their install and integrations in a
terminal beside a checklist. Nothing there needs a password. On the box
itself it is `berthd agents install --integrations codex`; `berthd agents
list` says which are there.

## With a pairing link

When berthd is already running on the box (the installer's link was used or
has expired, or another laptop already uses the box), run this on the box,
as the user berthd runs as:

```sh
berthd pair          # or ~/.local/bin/berthd pair, if ~/.local/bin isn't on PATH
```

It prints a link. On the laptop, paste it in the app (**Add a box**, under
"Paste what it printed"; pasting all of the output is fine), or:

```sh
berth pair 'berth://100.101.102.103:7444?code=…&fp=…' [--name my-box]
```

The link carries the box's fingerprint, so the laptop knows exactly which box
to trust, and a single-use code that expires after ten minutes (`--ttl`
changes that, up to an hour). How the code is proven without being sent is
in [the security model](/concepts/security#pairing).

## In the app

**Add a box** (in Settings → Boxes, the sidebar's Projects menu, or ⌘K), and
the first-run setup, show one screen with every way in:

1. When this Mac reaches a tailnet, **On your tailnet** lists its machines,
   each with **Set up** ([above](#on-your-tailnet)), and **Use this Mac**
   ([this Mac](#this-mac)) follows them. Without a tailnet, **Use this Mac**
   comes first.
2. **Or, on any box**: **On the box, run** the
   [install command](#with-the-install-command), with a copy button; then
   **Paste what it printed**: the link, or the whole output; Berth keeps the
   link. Enter pairs.
3. **Or let Berth set it up over SSH** takes `user@host` (Tab completes hosts
   from `~/.ssh/config` and machines on your tailnet), says which SSH agent
   or keys it will use before connecting, and runs `berth add ssh` with its
   output as it goes.

Without a tailnet, the install command comes first and **Or use Tailscale**
sits beside the SSH option. When a box can't be reached and might be on a
tailnet this computer isn't signed in to, Berth offers to sign in to that
tailnet and tries again.

## Where berthd listens

By default berthd listens on the box's tailnet address, port 7444, and
**refuses to start** if the box has none. To accept connections from the
internet, say so:

```sh
berth add ssh me@my-box --listen 0.0.0.0:7444   # from the laptop
berthd install --listen 0.0.0.0:7444                # on the box
```

Pairing is still required, and every connection still pins both keys; the
flag only changes who can attempt a handshake. `berthd doctor` warns about it.

## Boxes on another tailnet

A laptop's own Tailscale can only be on one tailnet. For boxes on another
(a personal tailnet while the laptop is on work's), the laptop agent runs an
embedded Tailscale node per network:

```sh
berth network login personal          # a one-time browser sign-in
berth discover --network personal     # machines there that could be boxes
berth add ssh me@homelab --network personal
```

Each box remembers the network it is reached through. Berth's own TLS still
runs on top; the tailnet only provides the route.

## Check it

```sh
berth boxes        # paired boxes and whether they are online
berth ping my-box  # it answers, and still trusts this laptop
berth doctor my-box
```

## On another computer

Using Berth on a second computer too? Don't pair each box again: make a join
link on the first one and paste it there. See
[more than one computer](/guides/more-computers).
